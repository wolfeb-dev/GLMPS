01

Govern, Don't Ban: The Sanctioned-Tool Decision

The most common AI governance mistake is banning unapproved tools with no alternative. This section explains why that approach fails and how to replace it with a sanctioned path that people will actually use.

Core principle

Give people an equally fast approved path. Then the defection to personal accounts stops.

The baseline report for {{CLIENT_NAME}} found shadow AI use — personal accounts, unsanctioned tools, or both. This is the norm in every mid-market company with no approved AI path. It is not a discipline problem; it is a procurement gap.

When the unapproved tool is faster, easier, or simply the one developers already know, banning it without a replacement does one thing: it drives the same usage underground, where you have zero visibility. The data leak happens either way. The difference is whether you can see it.

The goal of this playbook is to make the approved path the obviously better path — well-provisioned, well-documented, and fast enough that no one has a reason to defect.

What happens when you ban without an alternative
  • Developers continue using personal ChatGPT / Copilot — now on personal devices you can't monitor
  • The shadow AI footprint grows and becomes invisible to your DLP and GLMPS capture
  • Trust between security/IT and engineering erodes: security is seen as blocking productivity
  • High performers look elsewhere; AI-unblocked competitors hire them
  • When a data leak eventually occurs, you have no session data to investigate it
  • The ban is openly flouted within weeks; enforcement cost exceeds any risk reduction
What happens when you govern with a sanctioned alternative
  • Most developers switch to the sanctioned tool, because it's company-provisioned and supported
  • Sensitive-data flows through monitored, contract-protected accounts with no-train clauses
  • GLMPS has full session capture; egress events and policy violations are visible and alertable
  • Security and engineering share a common tool — the same one, with the same guardrails
  • Remaining shadow usage (holdouts, contractors) is identifiable as a residual gap, not the whole picture
  • Adoption metrics are measurable: you can prove the governance investment is working

02

Fast-Path Setup

Standing up the sanctioned tool and guardrails for a team of {{TEAM_SIZE}} developers. Target: first developer using the governed tool within one working day of kickoff.

1
Provision the sanctioned tool under company accounts

Create an organization/enterprise account for {{TOOL_NAME}} under a company email domain, not an individual's personal account. Assign a technical admin ({{ADMIN_NAME}}) who is not the same person as the billing owner.

  • Configure SSO so all user access goes through the company identity provider ({{IDP_NAME}}). This ensures joiners are provisioned automatically and leavers are deprovisioned immediately.
  • Enable the no-train and data-retention settings in the vendor console before inviting any users. Document the settings and save screenshots to the engagement record.
  • Confirm data residency region matches the client's data-handling requirements: {{REQUIRED_REGION}}.
2
Install and configure GLMPS on the representative dev environment

Run glmps init on the managed dev environment, dev container base image, or a representative sample of developer machines (minimum 3–5 machines across the team). GLMPS captures all AI harness sessions locally with no data leaving the building.

  • Verify the capture-parity matrix shows the sanctioned tool at full or high coverage. Coverage for {{TOOL_NAME}}: {{CAPTURE_COVERAGE}}.
  • Configure dev/prod zone classification using the paths identified in the Governance Starter Kit §02.
  • Enable the egress detector and live-install guard before inviting developers to use the new tool.
  • Confirm the alert center is active and test alerts route to {{ALERT_CHANNEL}}.
3
Deploy the AI Use Policy and instruction files

Distribute the signed AI Use Policy (Governance Starter Kit §01) to all staff with AI tool access. Require acknowledgment before account provisioning. This creates a documented consent chain.

  • Add the company's AI governance instruction file to the shared repository baseline — a CLAUDE.md, .cursorrules, or equivalent depending on the sanctioned tool. The policy in this file should match the written AI Use Policy, not supplement or contradict it.
  • Protect the instruction file at Layer 2: set it read-only in the managed environment, or add it to a CI check that alerts if it is removed or modified. An instruction file the agent can delete is advisory, not a control.
  • Schedule a 30-minute developer kickoff (see §03 for the agenda and do/don't guide).
{{INSTRUCTION_FILE_PATH}} — Enter the path to the instruction file that will be added to the client's repository. Example: "docs/ai-policy/CLAUDE.md" committed to the main branch with a CI lint check that fails if the file is absent.
4
Run the first week of monitored usage and review the baseline

Let the team use the sanctioned tool normally for 5 business days. GLMPS will build the first real baseline under the governed setup. At the end of the week, review the alert center with the technical lead.

  • Check: is the egress rate under the baseline threshold set in the Governance Starter Kit §02?
  • Check: are there any zone-crossing events (dev agents touching prod paths)?
  • Check: are there any quarantined injection flags that need review?
  • Tune the allowlist if there are recurring false positives from known-safe patterns.
  • Document the post-setup baseline: {{POST_SETUP_BASELINE_NOTES}}.
5
Wire the measurement loop and schedule the first quarterly review

Set a recurring calendar event for the quarterly AI posture review (see §04). Assign the owner for the review: {{REVIEW_OWNER}}. The first review compares against the Phase 1 baseline; subsequent reviews compare against the prior quarter.

  • Confirm the metrics defined in §04 are being captured and can be pulled from GLMPS at review time.
  • If the retainer is in scope: schedule the monthly monitoring check-in for the same day each month.
03

Team Enablement Guide

Hand this section directly to developers, engineering leads, and general staff. It covers how to use AI safely, where the sensitive data lives, and what the guardrails are watching for.

Tailor the do/don't lists to the specific sanctioned tool before distribution. If the tool is Claude Code, the examples below are accurate. If it is Copilot or Cursor, update the instruction file names and CLI commands accordingly.
Developers

How to use AI safely with company code

Safe practice
  • Use the company-provisioned {{TOOL_NAME}} account, accessed through your company SSO login. No personal accounts for work.
  • Paste code from internal, non-PII repositories freely — the vendor contract covers this data classification.
  • Review AI-generated code before committing, exactly as you would review a colleague's code. The AI makes mistakes. The PR reviewer will expect the same standard regardless of authorship.
  • Use AI to generate test cases, draft documentation, explain unfamiliar code, and stub out boilerplate — these are the highest-leverage, lowest-risk uses.
  • Flag unusual AI behavior to {{INCIDENT_CONTACT}} — if the AI appears to have "remembered" something it shouldn't, or suggests something that looks like it came from outside your context window, report it.
  • When in doubt about whether something is safe to paste, ask {{AI_POLICY_CONTACT}} rather than guessing.
What to avoid
  • Do not paste API keys, database passwords, private keys, or any production credential into any AI tool — including the sanctioned one. Use a secret manager instead.
  • Do not use your personal ChatGPT, Claude.ai, or Copilot account for anything involving company code or data. The company account has a no-train clause; your personal account does not.
  • Do not commit AI-generated code you haven't read. The guardrail is your review, not the AI's judgment.
  • Do not install new AI tools or plugins into your IDE without approval from {{APPROVAL_AUTHORITY}}. New tools appear in the GLMPS session map and are flagged.
  • Do not give the AI context it doesn't need — paste the relevant function or file, not the entire repository with credentials.
  • Do not share AI-generated client deliverables without disclosure if your client relationship requires it.
Engineering leads and team leads

Your role in AI governance

As a team lead, you are the first line of detection for AI misuse — not because you are policing your team, but because you are the person who reviews the code, sets the norms, and sets the example.

  • Review AI-co-authored code with the same rigor as human-authored code. Do not approve a PR faster because the AI wrote it or because it "looks right at a glance." AI outputs fail in specific, predictable ways: plausible-looking but subtly wrong logic, hallucinated library calls, security antipatterns that pass surface review.
  • Check the GLMPS alert center weekly (or delegate this to a rotation). Alerts that go unreviewed for more than {{ALERT_REVIEW_SLA}} are escalated to {{ESCALATION_CONTACT}}.
  • Set the norm on personal accounts explicitly and early. If you are still using a personal AI account for work, you are signalling that the policy doesn't apply to seniors. It applies to everyone.
  • When you see a teammate using an unsanctioned tool, surface it. The process is: report to {{INCIDENT_CONTACT}}, not a public callout. The goal is to get the person onto the sanctioned path, not to discipline them.
All staff

AI tools and company data — the short version

You may use the company-provisioned AI tool ({{TOOL_NAME}}) for work. You may not use personal AI accounts for work. The reasons:

  • When you use the company account, the vendor has agreed that your data will not be used to train their model. When you use a personal account, there is no such agreement.
  • The company account is monitored. If something goes wrong, we can investigate. A personal account is invisible to us.
  • If you are not sure whether something is okay to put into an AI tool, the rule is: would you put this in an email to a vendor? If not, don't put it in the AI tool either.

Questions go to {{AI_POLICY_CONTACT}}. Incidents (accidental pastes of sensitive data) go to {{INCIDENT_CONTACT}} within {{REPORTING_WINDOW}}.
