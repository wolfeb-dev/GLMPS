Artificial Intelligence Use Policy

Effective: {{EFFECTIVE_DATE}} Owner: {{POLICY_OWNER_ROLE}} Version: {{VERSION}} Next review: {{NEXT_REVIEW_DATE}}

1.1 Purpose

This policy establishes the rules for using artificial intelligence tools — including AI coding assistants, generative AI platforms, and AI-powered productivity tools — within {{COMPANY_LEGAL_NAME}} ("the Company"). It applies to all employees, contractors, and vendors who use company systems or process company data.

The goal is to enable teams to benefit from AI tools while protecting the Company from data exposure, legal liability, and security risk that arise from unmanaged AI use.

1.2 Scope

This policy covers:

  • AI coding assistants (GitHub Copilot, Claude Code, Cursor, Gemini CLI, Cline, and equivalents)
  • Generative AI chat and completion services (ChatGPT, Claude.ai, Gemini, Copilot Chat, and equivalents)
  • AI-powered features embedded in third-party software (e.g., AI-assisted search, auto-complete, summarization)
  • Any AI service accessed via a personal account on a company device or while processing company data

1.4 Acceptable Use

Employees may use sanctioned AI tools to:

  • Generate, review, refactor, and document code using company source code, within the permitted data classification for that tool.
  • Draft and refine written communications, documents, and summaries using non-confidential information.
  • Research, synthesize, and summarize information from public sources.
  • Automate repetitive tasks within the scope of the employee's role and the tool's permitted data classification.

1.5 Prohibited Use

The following are prohibited regardless of tool, account type, or urgency:

  • No personal accounts for company data. Using a personal AI account (personal ChatGPT Plus, personal Claude.ai, personal GitHub Copilot, etc.) to process company data, source code, customer information, or any non-public content is prohibited. Company data must only flow through company-provisioned, company-contractually-bound accounts.
  • No production secrets in AI prompts. API keys, database credentials, private cryptographic keys, bearer tokens, access tokens, and production environment configuration must not be pasted into any AI tool under any circumstances.
  • No regulated or sensitive personal data. Personally identifiable information (PII), protected health information (PHI), payment card data, and legally privileged communications are prohibited from AI tools without explicit written approval from {{PRIVACY_LEGAL_CONTACT}}.
  • No unreviewed AI-generated code in production. Code generated or co-authored by AI must pass the same review, testing, and approval process as human-authored code. AI authorship is not grounds for exemption from any gate.
  • No unsanctioned tools. Installing, trialing, or using AI tools not listed in §1.3 on company devices or with company data requires prior written approval from {{APPROVAL_AUTHORITY}}.

1.7 Incident Reporting

Report the following to {{INCIDENT_CONTACT}} within {{REPORTING_WINDOW}}:

  • Accidental submission of prohibited data (secrets, PII, regulated data) to any AI tool
  • Discovery that a team member is using an unsanctioned tool for company data
  • Unusual AI tool behavior — unexpected data reproduction, anomalous suggestions, or behavior suggesting prompt injection
  • Any alert generated by the AI monitoring system (GLMPS alert center)
Set {{INCIDENT_CONTACT}} to the team's security Slack channel, email alias, or ticketing queue. Set {{REPORTING_WINDOW}} to match the client's existing incident-response SLA — "4 business hours" is a reasonable default if they don't have one.

1.8 Enforcement and Acknowledgment

Violations of this policy may result in revocation of AI tool access and further disciplinary action under the Company's standard conduct policy. By using any AI tool within the scope of this policy, employees confirm they have read and agree to its terms. Re-acknowledgment is required annually or upon material policy update.

Control Durability: Defense-in-Depth Layers

Use this section when discussing with the client what will actually hold under real-world pressure — and what will not. The most common mistake in AI governance is treating instruction files as controls. They are not.

Every AI governance control lives at one of four layers, ordered below from weakest to strongest. Understanding this stack determines which gaps are cosmetic and which are structural.

Why instruction files alone are insufficient:

  • They are mutable by the very AI they constrain — an agent with write access to its own configuration can modify or overwrite the rules it operates under.
  • They are mutable by users — a developer under deadline pressure can edit the policy out of the file in seconds, with no audit trail.
  • They are vendor-specific — a CLAUDE.md is invisible to Copilot; a copilot-instructions.md is invisible to Cursor. Switch tools and the governance silently disappears, unless the same policy is written into every vendor's instruction file.
  • They are unmonitored — without a detective layer, nobody knows if the file has been changed, emptied, or if a new tool is in use that ignores it entirely.

Build all four layers. Never treat any single layer as sufficient on its own.

Layer 1
Advisory
Weakest — necessary, not sufficient

What it is: Instruction files (CLAUDE.md, AGENTS.md, .cursorrules, Copilot system prompts) that direct the AI's behavior. Also: developer training, written policy, and awareness programs.

What it provides: Improved defaults. A well-written instruction file reduces casual misuse and communicates intent. It is the lowest-cost layer to implement and should be the first one in place.

What it does not provide: Enforcement. The AI can be instructed to ignore it. The user can delete it. A different AI tool will not see it. There is no alert when it is changed.

Do this anyway, and do it deliberately: Write the same core policy into every vendor's instruction file so that a tool switch does not silently drop governance. A CLAUDE.md and a .cursorrules that say the same thing mean that switching from one to the other does not create a policy vacuum.

Examples in practice
  • CLAUDE.md rule: "Never read credential files. Never include secrets in prompts. Always ask before writing to production paths."
  • Copilot system prompt: "Do not suggest code that accesses production databases directly without explicit authorization."
  • Developer onboarding checklist: "Read the AI Use Policy before using any AI coding tool. Acknowledge annually."
Layer 2
Enforcing
Medium — blocks common violation paths

What it is: Technical controls that block prohibited actions at the tool or operating-system level. Hooks that intercept and reject actions before they execute. File-system permissions that prevent writes. Least-privilege credential scoping. A secret broker so the agent never holds the real credential.

What it provides: Real enforcement for the actions it covers. A hook that blocks writes to production paths will block them even if the instruction file has been deleted, and even if the developer forgot the policy exists.

What it does not provide: Coverage of paths not explicitly blocked. A hook on tool A does not protect tool B. Enforcing controls require maintenance as tools, paths, and workflows change.

Examples in practice
  • GLMPS live-install guard: a PreToolUse hook intercepts filesystem writes to registered production paths and blocks them unless the deploy bypass is explicitly active.
  • Secret broker (HashiCorp Vault, AWS Secrets Manager): the agent requests a time-limited, scoped token at runtime and never holds the root credential.
  • OS file permissions: credential files (e.g., ~/.aws/credentials, .env) set to read-only by owner, not accessible by the agent's effective user.
  • GLMPS file-API denylist: the API refuses to read or write secret-pattern paths even when they fall inside an otherwise-allowed root directory.
Layer 3
Environment
Strong — bad output cannot ship regardless of what the agent did locally

What it is: Infrastructure controls that constrain outcomes independently of what the AI or user does on their local machine. CI/CD gates and branch protection that block AI-generated code from reaching production without a human review. A managed dev container with policy and tooling baked into the image. A network-level egress or DLP proxy that inspects outbound traffic for sensitive data patterns.

What it provides: Outcome protection. Even if the AI produces something harmful and the developer commits it, the CI gate catches it before it ships. Even if an instruction file is deleted locally, the dev container reinstalls it on the next build.

What it does not provide: Visibility into what happened locally before the gate. A developer can still paste secrets into a prompt; the CI gate catches the output, not the input.

Examples in practice
  • Branch protection: no direct pushes to main; required PR review from a human who did not author or co-author the code with AI.
  • CI secret scanning: Trufflehog or GitGuardian in the pipeline; blocks any commit containing a detected secret pattern before merge.
  • Dev container: GLMPS installed in the base image; policy files present and protected; container rebuild restores them on next start.
  • Egress DLP proxy: inspects outbound HTTPS for PII or proprietary data signatures; alerts on or blocks submissions matching defined patterns.
Layer 4
Detective
Strongest — closes the loop; catches drift, new tools, and control failure

What it is: Continuous monitoring that verifies the other three layers are still in place, unmodified, and covering whatever AI tools are actually in use — and that alerts when they are not. This is the role GLMPS fills.

What it provides: Durability for the whole stack. Without a detective layer, you do not know when a developer adds a new unmanaged AI tool, when an instruction file is emptied, when a hook is disabled, or when egress has increased since the baseline assessment. Detective controls are the only layer that can catch what was not anticipated during setup.

What it does not provide: Prevention. A detective control generates an alert after the fact. For the highest-severity risks — production secret exposure, for example — pair it with enforcing or environment controls so detection does not arrive too late to matter.

Examples in practice
  • GLMPS continuous session monitoring: every AI agent session captured across harnesses, classified by zone and tool, surfaced in the session map. New or unmanaged tools appear immediately.
  • GLMPS alert center: egress events, zone violations, quarantined injection flags, and guard-status changes generate real-time alerts routed to the designated channel.
  • Memory integrity scan (GET /api/memory/scan): verifies GLMPS memory and configuration files have not been modified by injected content or unauthorized edits.
  • Quarterly AI posture review: compares current-state metrics against the baseline established in Phase 1; surfaces drift, new gaps, and guard efficacy since the last review.
The principle to leave with the client: Instruction-file edits are advisory, not controls. Governance with real teeth lives at the layers the agent cannot rewrite — enforcing hooks at Layer 2, CI/environment gates at Layer 3, and continuous monitoring at Layer 4. Layer 1 is the floor; it is not the ceiling.
